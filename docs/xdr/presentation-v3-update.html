What changed in the engine

Three defects that were costing you detections and memory.

Memory
15 GB → 224 MB

A record was built for every matched offset and held for the whole scan — then never written anywhere. On a match-heavy host that was 15 GB and still climbing. Re-measured with 2.5× more offsets: 224 MB peak.

Rule coverage
Rules ran that
had been skipped

A rule was dropped if any other rule in the same file merely mentioned an unavailable module — in a comment, or as a string to hunt for. Classification is now driven by the compiler's own error, not by scanning rule text.

Exit
Cancel and
clean up

Cancelling now drains and reports properly instead of returning early past the delivery check. Optional end-of-run host cleanup reclaims the working directory, gated on confirmed delivery.

The forensic record

One row per finding, not per matched byte.

An unanchored or short pattern can hit thousands of times inside a single file. The old schema wrote a dataset row for every one of them, repeating the same 18 columns of file and scan context each time.

Before — one row per offset
33,118

rows from one rule against one event log. On a fleet scan that exhausted the upload budget before other findings got a turn — three hosts lost data, one lost all of its matches.

Now — one row per (rule, file)
1

row, carrying match_count as the true uncapped total plus a capped sample of offsets and strings. Full per-offset detail still lands on the endpoint and in the evidence ZIP — nothing is lost.

  • Dashboards were corrected with it. Hit counts sum match_count rather than counting rows, so a rule with many string hits per file reports honestly.

Per-host sharding is not tidiness. It works around a server-side race.

  • The platform stages each write through a clone table. Two endpoints writing the same dataset collide, the server returns a transient error, and the rows are gone — not rejected. The retry returns success.
  • The cost we accept: a 500-endpoint fleet, with monthly rotation, creates on the order of a thousand datasets a month. That is what the next slide is for.

  • A scan is only touched once it is genuinely finished — terminal lifecycle row, or terminal Action Center state, and its newest row older than a settle window.
  • Verify before delete. Sources are removed only once the target's row count equals the sum of the sources. A mismatch keeps everything and reports it.
  • Dashboards are unaffected — they query yara_scanner_* wildcards, so shards and per-scan datasets fan in identically.

Retention

It deletes datasets. So the guard rails are the feature.

The platform has no undelete and no dataset versioning. Everything below exists because a wrong deletion cannot be walked back.

Rail 1–2

Never the current or a future month

A scan may be writing to it; clock skew must not destroy data.

Rail 3–4

Never unsuffixed, never a newer schema

An unsuffixed dataset holds a host's entire pre-rotation history.

Rail 5–6

Never foreign, never recently written

A rotation suffix records creation, not last write — a long scan is still writing.

Rail 7

Never an unconsolidated scan

If consolidation hasn't verified it, the shard is that scan's only copy.

  • Dry run by default. A bare invocation reports what it would delete and deletes nothing. Only an explicit affirmative enables deletion; an unrecognised value is rejected rather than guessed in either direction.
  • Both live rails fail closed. If the check query errors, the dataset is kept — the same skip-to-be-safe posture as every rail above it.
