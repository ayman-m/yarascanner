  • Merge time scales with dataset SIZE, not payload size. 15k rows ≈ 13 s/write; 77k rows ≈ 31 s/write — an unbounded append-only dataset eventually goes write-dead.

Payload killed mid-drain. 13,845 queued rows never sent — counted in dataset_delivery.undelivered, never silently dropped. The terminal lifecycle row still survives: it is sent inline, ahead of the queue.

  • Budget scan time + 10 minutes. Drain internals: 150 s minimum, 45 s per pending batch, capped at 600 s.
  • No scan_summary_<run_id>.json is itself the tell — it is written after the drain, so its absence means the run was killed before finishing.

Delivery accounting

The counters balance. There is no bucket for “vanished”.

The identity, enforced every run
queued == added + updated + skipped + unconfirmed + undelivered

Worked example from a real killed run: 1,523 queued = 1,504 delivered + 19 undelivered — and the 1,504 is 1,501 match rows plus initiated plus two heartbeats.

Check this one field

delivery_shortfall

Empty string means everything queued arrived. Non-empty names what did not — and says the findings are complete in the endpoint's local logs.

Never attempted

undelivered

Still queued when the run ended. This is the counter a too-short run timeout moves.

Not a bug

rows_unconfirmed

Read timed out mid-merge; the rows may have committed. Deliberately not retried — a blind retry duplicates them.

Consolidation

One pass is bounded — and does not resume itself.

Measured per-scan cost ≈ 128 s against a 900 s script timeout.

Default — comfortable
4

scans per pass · 403 s · 45% of the timeout budget.

Measured, tight
5

scans per pass · 638 s · 71% of budget. Little margin left.

The old default — unsafe
20

projects to ~2,552 s · 283% of budget. Killed around scan 7.

  • A pass killed mid-merge is not a clean failure. It leaves the consolidation lock held, and the pipeline parks until the 20-minute stale window clears it.
  • Verify before delete. Sources are removed only once the target's row count equals the sum of the sources — a mismatch keeps everything and reports it.
  • stopped_early means more remain. Re-run, or raise max_scans after measuring your own per-scan cost. The playbook runs Apply once per execution.

Where it stands

Validated end to end — with the gaps named.

Proven on a live tenant
  • Full round trip through the library-script path customers use — not a test harness
  • Overwrite model: 2,714 rows → 164, single scan_id, verified twice
  • Terminal row survives a mid-drain kill — committed 1 s before a 13,845-row drain began
  • Consolidation lock correctly refused a concurrent second pass
Open — stated, not smoothed over
  • A run outlived its 900 s timeout by ~8×. Observed once, mechanism unexplained
  • Does remove_data re-stamp _insert_time on surviving rows? Not load-bearing for the overwrite
  • The CLI --consolidate path has no max_scans bound — use --scan-id to scope it
Operational rule

A timed-out API call does not mean the script stopped. Check yara_scanner_consolidation_runs for a started row with no terminal row before intervening — especially before clearing a lock.
