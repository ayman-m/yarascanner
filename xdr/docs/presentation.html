Every endpoint, a YARA sensor.

xdr_yara_scanner.py — a multi-threaded YARA scanner that runs as a managed Cortex XDR response script and lands its findings as alerts and lookup datasets, with a CPU governor, cooperative cancellation and per-endpoint sharding.

Three inputs. Everything else ships with the script.

Operators fill in which rules, which folder, what severity. Alerts on or off, dataset on or off, CPU policy, sharding and tenant tag are set once in the CUSTOMER CONFIG block at the top of the file and travel with the upload.

yarafile

Base64-encoded rule pack. encode_rules.py in the repo does the encoding.

scan_folder

One path, a comma-separated list for multi-partition scans, or default. Invalid entries are skipped with a warning.

alert_severity

low · medium · high — the severity stamped on every alert this run raises.

A "pack" is one file, not a batch size. yarafile is a single base64-encoded .yar, compiled once at the start of the scan and held in memory for every file walked. The script imposes no rule-count limit and never splits a pack — 5,000 rules is one compile of 5,000 rules, not ten passes of 500. The 500 above is simply the largest pack in the test corpus.

Three channels, independently switchable.

Each output is a separate flag. Turning alerts off still writes the dataset; turning both off still writes the local forensic log.

Alerts → issues create_alerts

One alert per finding — rule + file, offset-free identity, hit count and sample inside. Feeds XDR incident creation and is idempotent across re-scans.

Matches dataset write_dataset

One row per matched string. Per-endpoint shard, monthly rotation. Queried across the fleet with the yara_scanner_matches* wildcard.

yara_scanner_matches_v2_<host>_<YYYYMM>

Scan lifecycle write_dataset

One row per state change — initiated, running, completed, cancelled, failed. This is where dashboards read scan state from.

yara_scanner_scans_v2_<host>_<YYYYMM>

Two different 500s — do not confuse them. The 500 here is CONFIG_ALERT_MAX_PER_SCAN, the alert storm cap: past 500 findings in one scan, per-finding alerts stop and each affected rule emits a single rollup alert instead — YARA Match Storm: <rule> carrying the suppressed count. It has nothing to do with how many rules your pack contains. Alert volume is bounded by design; nothing goes silent, and the dataset still records every match.

Local logging is never gated. logs/ and alert/ are written on every run whatever the flags say, plus a machine-readable scan_summary_<run_id>.json. Matched-file copies in the evidence ZIP are the one output that is off by default.

Use an Advanced key. Two of them.

Advanced keys sign every request with a nonce, a timestamp and a SHA-256 of the secret — a captured request cannot be replayed. The delivery key is embedded in a script that lands on every endpoint you scan, so it is scoped to write results and nothing else.

The permission that is not where you would look. insert_parsed_alerts is governed by External Issues Mapping, not by "Cases and Issues / Alerts" — verified on a live tenant, where a Cases-and-Issues key returns 403 on alert insert while dataset writes keep succeeding. Among built-in roles only Admin carries both required components, so create the custom role. Never deploy an Admin key to endpoints.

The scanner bounds its own share of the host.

Once a second the governor measures what it is using and what everything else is using, computes a target, and adjusts a sleep ratio. Workers sleep in proportion to the work just done — so the slowdown factor holds regardless of file size, disk or machine class.

On an idle Windows host you will see ratio 0.0 — that is correct. The Cortex agent already pins payload processes to 2 cores, so the scanner cannot exceed ~25% of an 8-core machine and a 70% headroom target is unreachable. Under real load it does engage: at 86% external load the target floored at 5% and the scanner was held to 6.6–9.2%.

Cancelling from the console does stop the scan.

It terminates the payload process on the endpoint. There is no graceful shutdown, no cleanup hook and no chance to flush — which is why what you lose is predictable, and why the record it leaves behind looks the way it does.

No handler can be installed

The agent runs Action Center scripts on a worker thread named script_thread. Python's signal.signal() raises "signal only works in main thread of the main interpreter" — on Windows and Linux alike.

Windows would not honour one anyway

Termination is TerminateProcess, which by design cannot be intercepted. There is no cleanup hook available at any layer, so no amount of scanner code can close that row.

What to do about it

Treat a lifecycle row with no terminal state and no recent heartbeat as stale, not running. Filter "scans in progress" widgets on heartbeat age, and reconcile after any console Cancel.

Your rules compile locally. The agent disagrees.

The Cortex agent ships its own embedded Python and its own compiled libyara. Module availability is a compile-time property of that build — not of Python, and not of the script. A rule importing a missing module fails to compile, and the scanner skips that rule rather than failing the scan.

These are shared-tenant characteristics of the Cortex APIs, not scanner settings. The scanner is built to degrade visibly against them — but a rule pack that matches far more than intended is what takes you there.

Alert budget

~600/min

Per API key, shared across every endpoint using it. A thousand endpoints on one key share one budget. Batches are paced and retried; past the window the remainder is counted undelivered.

Dataset write time

grows with size

Each add_data triggers a server-side merge whose duration scales with the dataset's total size — ~13 s at 15k rows, ~31 s at 77k. Monthly rotation is what keeps this flat.
