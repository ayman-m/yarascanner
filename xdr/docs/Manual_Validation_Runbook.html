Before you start
  • A test endpoint you may scan freely. Not production.
  • Console access to Action Center and XQL Search.
  • Scanner uploaded with a Standard key; 5 automations with an Advanced (HMAC) key.
  • A base64 YARA rule file you know will match something.

A rule that matches nothing makes most of this untestable. For a throwaway test rule, a broad string like "localhost" or "Copyright" matches on any host. Validation only — never ship it.

Find your dataset names first

Settings → Data Management → Dataset Management, filter yara_scanner. You want a pair:

yara_scanner_matches_v4_<host>_<6hex>          ← no month. Correct.
yara_scanner_scans_v4_<host>_<6hex>_<YYYYMM>   ← month. Also correct.

They will not exist until your first scan — the scanner creates them. Below, MATCHES and SCANS mean those two names.

PART A

Deployment checks

No scans yet. Cheap, and catches the config mistakes that waste an afternoon.

10 minNon-destructive
A1Scanner version
Do

Action Center → Scripts → your scanner → check __version__ in the body.

Expect

3.4.0

Fails if

Anything lower. Later parts assume v4 behaviour older builds don't have.

A2Five automations, and no stragglers
Do

Settings → Automations, search Yara.

Expect

Exactly five: YaraReport, YaraConsolidateStatus, YaraConsolidateApply, YaraConsolidateSummary, YaraCleanup.

Fails if

You see YaraConsolidateFast — removed; you're on an old pack.

A3Credentials — fastest test that finds a wrong key
Do
!YaraReport
Expect

A dataset inventory table. On a fresh tenant it may legitimately say 0 current-schema datasets — still a pass, because it proves the key authenticated.

Fails if

HTTP 401. A Standard key in an Advanced slot, a typo, or a rotated key — the message can't distinguish them. Regenerate an Advanced key and re-edit all five.

A4Scanner key has Query Center
Do

Settings → Configurations → API Keys → your scanner key's role. Confirm Query Center (investigation_query_view) alongside External Issues Mapping and Data Management.

Fails if

Absent. The scan still runs and still writes — but the start-of-scan overwrite 403s, fails safe, and the dataset quietly accumulates. Part C is where you'd find out the hard way.

PART B

First scan

15 minNon-destructive
B1Run a small scan
Do

Action Center → your scanner → Run, targeting the test endpoint. scan_folder: something small — /etc on Linux, C:\Windows\System32\drivers\etc on Windows. alert_severity: low.

Set the action timeout to 30 minutes even though this is quick — Part D explains why, and there's no reason to learn it on your first run.

Expect
SCAN_RESULT: Scan completed: <N> files scanned |
  0 rules failed compilation | <M> matches found | ...
Fails if

0 rules failed compilation isn't 0 → your rules use a module the agent's YARA lacks (4.1.0 on Windows/macOS, 3.11.0 on Linux). Fix before continuing — everything downstream needs matches.

B2Lifecycle rows landed
Do
dataset = <SCANS>
| fields scan_id, status, files_scanned, _insert_time
| sort desc _insert_time
| limit 10
Expect

At least two rows for one scan_id — initiated and a terminal completed.

Fails if

No completed row. Either still running, or the payload was killed — check for the summary file (B4); its absence confirms a kill.

Not a bug

Rows may appear out of order — completed can carry an earlier _insert_time than initiated. Deliberate: the terminal row is sent inline, ahead of the upload queue, so it survives even if the queue never drains.

B3Match rows landed
Do
dataset = <MATCHES>
| comp count() as rows, sum(rule_count) as rule_file_pairs,
       sum(match_total) as string_hits by scan_id
Expect

One row, one scan_id, rows > 0.

Reading it: these three deliberately differ. rows is matched files; rule_file_pairs is the (rule, file) findings behind them; string_hits is every individual string match. rows ≤ rule_file_pairs ≤ string_hits is the v4 grain working — not loss.

Fails if

More than one scan_id (only one scan has run), or rows is 0 while the scan reported matches.

B4Delivery accounting on the endpoint
Do

Read the summary file on the endpoint:

Windows  C:\yara_scanner\logs\scan_summary_<run_id>.json
Linux    /opt/yara_scanner/logs/scan_summary_<run_id>.json
macOS    /usr/local/yara_scanner/logs/scan_summary_<run_id>.json
Expect 
"scanner_version": "3.4.0",
"outcome": "completed",
"delivery_shortfall": "",
"dataset_delivery": { "queued": N, "records_added": N,
                      "undelivered": 0, ... }

The two that matter: delivery_shortfall is an empty string, and queued == records_added.

Fails if

delivery_shortfall non-empty → rows never reached the tenant. It names how many and confirms the findings are complete in the endpoint's local logs. Usually a too-short timeout — see Part D.

File missing entirely → the run was killed before finishing. It's written after the drain, so its absence is itself the diagnosis.

PART C

Prove the overwrite

The behaviour most people don't believe until they see it.

10 minNon-destructive
C1Note the current state
Do
dataset = <MATCHES> | comp count() as rows by scan_id

Write down the scan_id and rows.

C2Scan the same host again
Do

Run exactly the same scan as B1 — same host, folder, rules.

C3Confirm replacement, not accumulation
Do

The same query as C1.

Expect

Still exactly one scan_id — the new one. The first scan's rows are gone.

Fails if

Two scan_ids → the overwrite didn't happen. Check A4 (Query Center). Without it the flush 403s silently and the dataset accumulates — precisely what this test exists to catch.

C4Confirm the scans dataset did the opposite
Do
dataset = <SCANS> | comp count() as rows by scan_id
Expect

Two scan_ids — both scans. The lifecycle dataset is append-only and must not be overwritten.

Together

C3 and C4 are the whole dataset model in two queries: matches replaced, scans accumulated.

PART D

Delivery under load

Finds the problem most likely to cost you data in production.

45 minNon-destructive
D1A scan large enough to queue a real backlog
Do

Run against /usr (Linux) or C:\Windows (Windows). Set the timeout generously — 60 minutes; you're testing delivery here, not timeout behaviour. Note the wall-clock time from launch to the action completing.

D2Compare scan time against total time
Do

In the summary JSON, read duration_secs. Compare to your measured wall-clock.

Expect

Wall-clock meaningfully longer than duration_secs. That gap is upload drain.

Reference: a 93,137-file scan took 169 s to scan and 401 s to drain — 2.4×. Your ratio will differ; the existence of the gap is the point.

D3Confirm nothing was lost
Do

Check delivery_shortfall and dataset_delivery as in B4.

Expect

Shortfall empty, undelivered: 0.

D4Now size your real timeout
Do

You've just measured your own scan-to-drain ratio, on your hardware and link. Use it:

action timeout ≥ expected scan + measured drain + margin

Starting point: scan estimate + 10 minutes. Drain internals cap at 600 s, but a large backlog plus retries can approach it.

Optional — prove the failure mode

Re-run D1 with the timeout deliberately short (say 5 min on a scan you know runs longer). Expect: the action is killed, no summary file is written, and the scans dataset still receives its terminal row. That last part is the inline-send working.

PART E

Dataset management — read-only

10 minNon-destructive
E1Inventory
Do
!YaraReport
Expect

Every yara_scanner_* dataset with kind, host and state. Your live matches dataset should read as a permanent / overwrite dataset — not "not rotated".

Fails if

It says not rotated (no YYYYMM) — set CONFIG_LOOKUP_ROTATION="monthly" for your v4 matches dataset. Wrong for v4 — you're on an old pack. (For a v2/v3 dataset that message is correct.)

E2Readiness
Do
!YaraConsolidateStatus
Expect

Eligible scan count, plus any in progress or blocked, with reasons.

On a fresh or freshly-wiped tenant: 0 scan(s) eligible to consolidate, with every count 0 and every scan-ID list empty. The correct result, not a misconfiguration — a tenant with no host matches or scans datasets gives the gate nothing to evaluate.

Reading it: a scan you just ran often shows as not eligible. Correct — a 900-second quiet period stops consolidation racing a still-draining uploader. Wait it out rather than working around it.

PART F

Consolidation

30 minDeletes data
This part deletes data

YaraConsolidateApply has no dry-run mode. There is no execute argument. A bare invocation merges and deletes source shards immediately.

Run against test scans you are willing to lose. Deleted datasets cannot be recovered — the platform has no undo.

F2 and F3 are not one job at two settings

They read different datasets, write different targets, and only one of them deletes. On v4 you run both — picking one is not the decision on offer.

YaraConsolidateSummary — F2YaraConsolidateApply — F3
Readsthe per-host matches dataset (plus the scans shards, to see which scans have finished)the monthly scans lifecycle shards
Writesyara_scanner_summary_v4_scan_<id>yara_scanner_scans_v4_scan_<id>
Deletesnothing, everthe scans shards it merged, once verified

The v4 per-host matches dataset carries no month suffix, so Apply never classifies it as a shard: it never enters a consolidation or deletion list, and no Apply run merges it or deletes it. The warning above is about your scans shards. (Apply's matches path is still live code and would fire on a month-suffixed matches shard — schema v2/v3, or dated v4 debris. A current-model tenant has none.)

That leaves Summary as the only automation that writes a durable per-scan record of what matched. A scan's file-level detail is never lost to consolidation — it is lost to the next scan on that host, which overwrites the matches dataset wholesale, and on v4 nothing archives it first.

F1Preview first (safe)
Do
!YaraConsolidateStatus

Note the eligible scan_ids — the scans F3 will merge. Summarise them in F2 first: not because F3 would delete their matches, but because the next scan on that host will overwrite them and F2 is the only thing that keeps a record.

F2Summary — record what matched (non-destructive)
Do
!YaraConsolidateSummary execute="false"

Then for real:

!YaraConsolidateSummary execute="true"
Expect

Dry run reports what it would write. The real run writes to yara_scanner_summary_v4_scan_<id> and reports host shards deleted: 0 — summary mode never deletes.

Verify the source survived:

dataset = <MATCHES> | comp count() as rows by scan_id

Unchanged. That's the proof summary mode is safe to schedule.

F3Apply — merge the scans lifecycle shards (destructive)
Do
!YaraConsolidateApply max_scans="4"

Pass max_scans explicitly the first time even though 4 is the default — it makes the bound visible in the War Room record.

Expect

N scan(s) consolidated, and if more remain, "Pass was bounded… Run again to continue."

Verify the target holds the merged rows:

dataset = yara_scanner_scans_v4_scan_<slug> | comp count() as rows

The count should match that scan's rows across the source scans shards. Do not go looking for a yara_scanner_matches_v4_scan_<slug> dataset — earlier revisions of this runbook told you to; on v4 it is never created, and querying it returns a dataset-not-found error that reads exactly like a failed consolidation.

Verify the sources went: run !YaraReport. The month-suffixed yara_scanner_scans_v4_<host>_<hex>_<YYYYMM> shards that held only this scan are gone; the new ..._scan_<slug> target is listed as a per-scan consolidated target. A shard that also holds a scan you did not consolidate is deliberately kept — the log says "kept shard … N of M scan(s) still pending consolidation". That is correct, not a failure.

Verify what Apply left alone:

dataset = <MATCHES> | comp count() as rows by scan_id

Identical to F2 — same dataset, same single scan_id, same row count. The per-host matches dataset is never a consolidation source on v4 and is never deleted.

F4Confirm the run was recorded
Do
dataset = yara_scanner_consolidation_runs
| fields _insert_time, status, consolidated_count, failed_count
| sort desc _insert_time | limit 5
Expect

A started row and a terminal row (success / partial_failure).

Reading it: a started row with no terminal row means a pass was killed — or is still running. That pairing is the diagnostic you'll rely on in production.

F5Drain the backlog
Do

If F3 said more remained, run it again until it stops saying so.

Expect

Each pass consolidates up to max_scans and reports what's left. It does not resume itself — by design, not a bug.

PART G

Prove the safety rails fire

The most valuable part. A guard you have never seen trigger is a guard you are trusting on faith.

20 minPartly destructive
G1The consolidation lock
Do

Start !YaraConsolidateApply and, while it runs, start a second one from another War Room tab.

Expect

"Skipped this pass — the consolidation lock is held by another concurrent run." and nothing touched.

Why it matters: without this, two runs could both delete sources after only one wrote a target.

G2Cleanup refuses to delete without opt-in
Do
!YaraCleanup older_than_months="0"
Expect

A report of what it would delete, and nothing deleted — execute defaults false. Verify the named datasets still exist.

G3Cleanup will not touch your live matches dataset
Do

In the G2 output, find your live MATCHES dataset.

Expect

It appears in the skipped list, reading:

permanent per-host matches dataset - the scanner
REPLACES it wholesale ...
Fails if

It appears as a deletion candidate. Stop — do not run YaraCleanup with execute=true. That guard protects your deep-dive source.

G4Cooperative cancel writes a terminal row
Do

Start a long scan. While it runs, run the same script with Entry Point = cancel (no inputs) on the same endpoint.

Expect

Within ~5 s it stops with Scan cancelled by operator, and:

dataset = <SCANS> | fields scan_id, status
| sort desc _insert_time | limit 5

shows a terminal cancelled row.

Contrast — not on a scan you care about

The Action Center console Cancel button hard-kills the payload and writes no terminal row, leaving the scan showing running until the 24-hour abandoned cutoff. That difference is exactly why the cancel entry point exists.

G5Schema-version mismatch — the two directions differ
Do (safe direction — too LOW)
!YaraConsolidateStatus schema_version="2"
Expect

0 current, and your v4 datasets reported as newer schema — never pruned. Nothing touched.

Why: anything newer than the assumed current version is something this build doesn't understand, so it refuses to act. This is the safe failure, and the one you'll hit in practice. It is also silent — a run reporting 0 candidates and exiting cleanly can mean a version mismatch rather than an empty backlog.

The other direction is not safe — don't test it casually

Setting schema_version too HIGH (say 9 against v4 data) reclassifies every live dataset as legacy — and legacy is eligible for deletion via YaraCleanup's delete-legacy path.

Rails still stand between that and loss: blanket legacy deletion is refused outright if any newer-schema dataset exists; unsuffixed datasets (yours is one) are never candidates; per-scan targets, the current month and future months are never candidates; execute still defaults false. Verify by reading the skip reasons, not by running a real delete.

Before production
  • Timeout sized from your D2 measurement, not the reference figure
  • Both consolidation automations scheduled, and understood as different jobs — Summary for the per-scan record of what matched, Apply for the scans lifecycle shards. Not alternatives: Apply never writes or deletes the per-host matches dataset, so scheduling it alone leaves no record of any scan's matches once the next scan overwrites that host
  • Everyone who can run automations knows Apply has no dry-run mode
  • YaraCleanup scheduled — if at all — in its own window, never alongside the merge
  • Test rules removed; only real detection content ships
  • A plan for draining a backlog larger than one bounded pass
